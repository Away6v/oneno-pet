# 04 · 更新与发版

> 本文涵盖「检查版本 + 一键升级」的**实现方式**，以及**日常发版的操作步骤**。
> 分发走**公开仓库的 GitHub Releases**，不需要自建服务器。

---

## 1. 功能概述

- 在「设置 → 软件」页可查看当前版本、手动检查更新
- 发现新版本时可一键升级：自动下载 → 验签 → 静默安装 → 重启应用
- 可选「自动检查更新」（默认开启）：打开设置窗口时静默检查一次，**只提示，不自动安装**

---

## 2. 原理：为什么不需要服务器

Tauri v2 官方更新器（`tauri-plugin-updater`）只需要两样东西：

1. 一个 HTTPS 可访问的**版本清单 JSON**（约定叫 `latest.json`）
2. 清单里指向的**安装包下载地址**

公开仓库的 GitHub Releases 免费提供这两样，而且有固定链接：

```
https://github.com/Away6v/oneno-pet/releases/latest/download/latest.json
```

`releases/latest/download/<文件名>` 永远指向最新的**正式** Release（不含草稿与预发布）。发新版后客户端读同一个地址即可拿到新清单，**不需要改客户端代码，也不需要任何服务器**。

安全性由 **minisign 签名**保证：安装包由发布方用**私钥**签名，客户端用**编译进程序的公钥**验签，不通过会直接中止，不会安装。

> ⚠️ **地址一次定终身**：`endpoints` 写在 `tauri.conf.json` 里，会被编译进客户端二进制。已经发出去的老版本只认当时那个地址，之后改地址等于让老用户永久失联。

## 3. 实现清单

### 3.1 Rust 侧

| 文件                                   | 内容                                                                       |
| -------------------------------------- | -------------------------------------------------------------------------- |
| `src-tauri/Cargo.toml`                 | 声明 `tauri-plugin-updater`、`tauri-plugin-process`                        |
| `src-tauri/src/lib.rs`                 | 注册两个插件；`open_url` 命令（用系统默认浏览器打开下载页，零额外依赖）     |
| `src-tauri/tauri.conf.json`            | `bundle.createUpdaterArtifacts: true`；`plugins.updater` 配置              |
| `src-tauri/capabilities/settings.json` | `updater:default`、`process:allow-restart` 权限（仅设置窗口可用）          |

`plugins.updater` 的实际配置：

```json
{
  "plugins": {
    "updater": {
      "pubkey": "<minisign 公钥内容>",
      "endpoints": [
        "https://github.com/Away6v/oneno-pet/releases/latest/download/latest.json"
      ],
      "windows": {
        "installMode": "passive"
      }
    }
  }
}
```

- `pubkey` 必须是**公钥内容本身**，不能写文件路径
- `installMode: "passive"`：安装时显示带进度条的小窗口，无需用户交互。NSIS 采用默认的 `currentUser` 安装模式，因此静默升级不会弹 UAC

### 3.2 前端

| 文件                      | 内容                                                                          |
| ------------------------- | ----------------------------------------------------------------------------- |
| `package.json`            | 声明 `@tauri-apps/plugin-updater`、`@tauri-apps/plugin-process` 与版本脚本     |
| `src/types.ts`            | `AppConfig.autoCheckUpdate`；下载页常量 `RELEASE_PAGE_URL`                     |
| `src/settings.ts`         | 版本更新模块（检查 / 下载 / 安装 / 重启 + 状态机）；版本号用 `getVersion()` 读取 |
| `settings.html`           | 「软件」页的「版本更新」卡片                                                   |
| `src/styles/settings.css` | 更新卡片样式，各区块按 `#upd-detail` 的 `data-state` 显隐                       |

**版本号单一来源**：以 `tauri.conf.json` 的 `version` 为唯一权威，前端通过 `getVersion()` 读取，不在前端硬编码。

### 3.3 发布流水线

`.github/workflows/release.yml`：推送 `v*` 标签触发

```
npm ci → 校验版本号一致 → 校验 tag 与版本号一致 → tauri-action 构建 + 签名 + 上传 Release + 生成 latest.json
```

> 第二道校验（`sync-version --check`）只管 `tauri.conf.json` / `package.json` / `Cargo.toml` **三者之间**一致；
> 第三道才管 **tag 名**，比较 `v$(tauri.conf.json 的 version)` 与 `${GITHUB_REF_NAME}`，不一致直接失败。
> 少了这道，tag 打在没改版本号的 commit 上会**静默成功** —— 包和 `latest.json` 里还是旧版本号，客户端永远说「没有新版」。
> 另外 Windows runner 上这步必须写 `shell: bash`（默认是 pwsh）。

### 3.4 辅助脚本（`scripts/`）

`version-files.mjs`：版本号读写的公共模块（四个文件的定位正则 + 读写 + 一致性校验），供下面两个脚本共用。四个文件里被替换的字段都只出现一次，所以一律用「首个匹配 + 字符串替换」而非 `JSON.parse` + `stringify`，以保住原排版与换行符。

`set-version.mjs`：**改版本号的首选入口**，一条命令改完四处。

```bash
npm run set-version -- 0.1.1            # 直接给版本号
npm run set-version                     # 交互式输入
npm run set-version -- 0.1.1 --dry-run  # 只看会改什么，不落盘
npm run set-version -- 0.0.9 --force    # 允许把版本号调低（默认拒绝）
```

改动范围：`src-tauri/tauri.conf.json`（权威）→ `package.json` → `src-tauri/Cargo.toml` → `src-tauri/Cargo.lock`。
内置三道保护：

- **拒绝降级**：新版本低于当前版本时直接退出，除非加 `--force`（更新器只认更高的版本号，降级会让老客户端永久收不到更新）
- **拒绝非法版本号**：必须是 `x.y.z` 形式
- **收尾自校验**：改完自动跑一遍一致性检查，不一致就以非 0 退出

脚本**只改文件、不碰 git**，最后会打印该敲的提交 / 打 tag / 推送命令（remote 名从 `.git/config` 里读，不写死）。

`sync-version.mjs`：把 `tauri.conf.json` 的版本反写到其余文件（`set-version` 的底层能力，也可单独用）。

```bash
npm run sync-version             # 同步
npm run sync-version -- --check  # 只校验（CI 使用）
```

> 注意 `--check` 只比对 `tauri.conf.json` / `package.json` / `Cargo.toml` 三者，**故意不含 `Cargo.lock`** ——
> 那个文件由 cargo 自动维护，不该拦住发版。

`build-desktop.mjs`：本地打包入口（`npm run build:desktop`）。开启 `createUpdaterArtifacts` 后本地打包也强制要签名，脚本会从 `~/.tauri/oneno-pet.key` 读私钥、注入 `TAURI_SIGNING_PRIVATE_KEY` 与空的 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`，再调 `tauri build`。

实测踩到的两个坑，脚本已内置处理：

1. **只设 `TAURI_SIGNING_PRIVATE_KEY_PATH` 不生效**（CLI 2.11.5），打包末尾照旧报「no private key」，必须把私钥**内容**填进 `TAURI_SIGNING_PRIVATE_KEY`。
2. **不给密码变量就会卡住**：stdin 是终端时 CLI 会打印 `Decrypting updater signing key, expect a prompt for password` 并等输入，在后台/CI 里表现为无限挂起。脚本默认补空密码；私钥真有密码就自己 export `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 覆盖。

私钥不在默认位置时用 `ONENO_SIGNING_KEY=<私钥路径>`；只想本地快速验证、不要升级包时用 `npm run build:desktop -- --no-sign`。

本地打包的产物只有两样：

```
src-tauri/target/release/bundle/nsis/
  oneno-pet_0.1.1_x64-setup.exe       ← 安装包
  oneno-pet_0.1.1_x64-setup.exe.sig   ← 升级用签名（NSIS 直接用 exe，不再有额外 zip）
```

> **`latest.json` 不会在本地生成**，它由 CI 里的 `tauri-action` 产出并随 Release 上传。
> 所以「本地打一个包 → 客户端就能检查到更新」是走不通的，验证升级必须走第 6 节的发版流程。
> 本地打包的价值是：确认能出包、能签名、代码没问题。

`wait-release.mjs`：**盯 tag 触发的 CI 构建**（`npm run wait-release`）。
推完 tag 后不用刷网页，它每 15 秒查一次，只在状态有变化时打印一行，跑完给出结论。

```
npm run wait-release                        # 盯最新一次 tag 构建
npm run wait-release -- v0.1.1              # 盯指定 tag
npm run wait-release -- --once              # 只看一眼当前状态
npm run wait-release -- --timeout 1200      # 最长等 20 分钟（默认 15）
npm run wait-release -- --token <令牌>      # 用令牌调 API（配额 60/小时 → 5000/小时）
```

退出码：`0` 成功 / `1` 构建失败或验签不配对 / `2` 超时。跑完还会顺带做两件事：

1. **报告发布状态** —— 判断这个 tag 是否已经 Publish 成 latest，没发布就打印编辑页直达链接
2. **验签自检** —— 把 `tauri.conf.json` 里的客户端公钥与 `latest.json` 里签名的 minisign keyID 比一遍。
   两者不是一对的话，更新会一路下载成功、最后卡在验签，现象很有迷惑性，所以自动查掉

> 实现要点：`<app>.key.pub` 与 `latest.json` 的 `signature` **本身就是整份文件的 base64**
> （内容形如 `untrusted comment: ...\n<base64>`），要**解两层**才能拿到字节流；
> keyID = 字节流第 3~10 字节（hex 大写）。只解一层会得到 `untrusted comment` 的 ASCII 字节，是个隐蔽的错。
>
> 另一个限制：**草稿在匿名 API 里完全查不到**（`GET /releases` 不返回 draft、
> `GET /releases/tags/<tag>` 对草稿 404），所以脚本**无法**确认草稿是否已生成，
> 只能判断「是否已发布」。想确认草稿存在只能开网页。

**配额怎么处理的：** 匿名调 GitHub API 只有 **60 次/小时**，而一轮「等 CI」要查约 30 次 —— 排查几次就会把配额烧光，连脚本自己都跑不起来。所以：

| 机制         | 做法                                                                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 启动先探配额 | `GET /rate_limit` **不计入配额**，免费。探到剩 0 且重置时间在 `--timeout` 内 → 自己等到重置再继续；超出就报错并给出三条自救路径                          |
| 动态降频     | 每个响应都带 `x-ratelimit-remaining`，顺手记下（**不额外发请求**）。剩 >25 → 15 秒；>12 → 30 秒；再低 → 60 秒，并停止拉步骤详情                          |
| 令牌         | `--token` 参数 / `GITHUB_TOKEN` / `GH_TOKEN` 任一即可把配额提到 5000/小时。公开仓库只读，**令牌不需要勾任何 scope**                                        |

> 也就是说：**配额紧的时候脚本会自己变慢而不是报错**，并且会打印一行说明，不会让人以为卡死了。

## 4. 界面与状态机

界面状态写进 `#upd-detail` 的 `data-state`，CSS 据此显隐各区块：

| 状态          | 界面表现                                                          |
| ------------- | ----------------------------------------------------------------- |
| `idle`        | 不占位（只显示「当前版本 + 检查更新」一行）                        |
| `checking`    | 「正在检查更新…」，按钮变「检查中…」并禁用                        |
| `upToDate`    | 「已是最新版本 v0.1.0」                                            |
| `available`   | 「发现新版本 v0.1.1，可一键升级」+ 更新说明 + 「立即升级」/「稍后」 |
| `downloading` | 进度条 + 百分比                                                    |
| `installing`  | 「正在安装，软件即将重启…」                                        |
| `error`       | 红色错误文案 + 「重试」/「手动下载」                              |

「手动下载」会调用 Rust 的 `open_url` 命令，用系统默认浏览器打开 Release 页面 —— 这是国内网络不通时的兜底出口。

自动检查（打开设置窗口时触发）失败时**静默处理**，不弹错误，只有手动点「检查更新」才会显示失败原因。

> 下载中断会自动重试一次（`MAX_ATTEMPTS = 2`）：中国大陆直连 GitHub 附件域名时常在中途断流，
> reqwest 把它渲染成 `error decoding response body`，字面意思极具误导性。该错误会被翻译成
> 「网络中断，下载没完成」并给出「手动下载」出口。若下载已完成才失败（问题在安装阶段），则不重试。

## 5. 首次发布前必须做的两件事

### 5.1 备份签名私钥

密钥对存放在用户主目录下：

| 文件                         | 用途                     | 是否可公开     |
| ---------------------------- | ------------------------ | -------------- |
| `~/.tauri/oneno-pet.key`     | 给安装包签名             | **绝不可泄漏** |
| `~/.tauri/oneno-pet.key.pub` | 客户端验签（已写入配置） | 可公开         |

> ⚠️ **私钥丢失 = 再也无法给老用户推送更新**（老客户端只认当时那把公钥）。
> ⚠️ **私钥泄漏 = 任何人都能伪造更新推送给你的用户**。

请把私钥备份到密码管理器或加密盘。`.gitignore` 已加入 `*.key` 防呆。

### 5.2 配置 GitHub Secrets

在仓库 `Settings → Secrets and variables → Actions` 新增：

| Secret 名                   | 值                             |
| --------------------------- | ------------------------------ |
| `TAURI_SIGNING_PRIVATE_KEY` | 私钥文件的**全部内容**（文本） |

当前私钥未设密码，因此**不需要** `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。

## 6. 发版流程

> 本仓库的 git remote 名是 `oneno-pet`（**不是 `origin`**），分支为 `main`。
> 全流程约 10 分钟，其中约 7 分钟是在等 CI —— 这段时间用 `npm run wait-release` 盯着，不用刷网页。

### 6.1 速查（照抄这六步）

```bash
# ① 改版本号：tauri.conf.json + package.json + Cargo.toml + Cargo.lock 一次改完
npm run set-version -- 0.1.1

# ② 提交并推送代码（必须先提交，tag 指向的是 commit）
git add -A && git commit -m "chore: 版本号 0.1.1"
git push oneno-pet main

# ③ 打 tag 并推送 → 触发 CI
git tag v0.1.1
git push oneno-pet v0.1.1

# ④ 盯 CI 跑完（约 7~8 分钟）。跑完会直接告诉你「能不能去发布了」
npm run wait-release -- v0.1.1

# ⑤ 发布：草稿卡片右上角「铅笔」图标 → 编辑页最底部 → Publish release
#    直达链接：https://github.com/Away6v/oneno-pet/releases/edit/v0.1.1

# ⑥ 验证清单已上线
curl -sL https://github.com/Away6v/oneno-pet/releases/latest/download/latest.json
```

> ⚠️ 第 ③ 步**只推 tag，不要顺手去网页上建 Release**（原因见第 9 节铁律 2）。

### 6.2 详细步骤

**步骤 1 · 决定版本号**

- 三段数字 `主.次.修订`，如 `0.1.1`
- **必须严格大于当前版本**。脚本会拒绝降级（除非加 `--force`），因为更新器只认更高的版本号，降级会让已发布的客户端永远收不到更新
- **不要复用已发布过的版本号**。客户端会认为「没有新版」
- **tag 名必须正好是 `v` + 版本号**（如版本 `0.1.1` → tag `v0.1.1`）。CI 会校验，对不上直接失败

**步骤 2 · 改版本号**

```bash
npm run set-version -- 0.1.1
```

也可以不带参数，脚本会提示你输入：`npm run set-version`。只想先看看会改什么，加 `--dry-run`。

**预期输出：**

```
版本号  v0.1.0 → v0.1.1

  src-tauri/tauri.conf.json    0.1.0 → 0.1.1
  package.json                 0.1.0 → 0.1.1
  src-tauri/Cargo.toml         0.1.0 → 0.1.1
  src-tauri/Cargo.lock         0.1.0 → 0.1.1

  ✓ package.json  0.1.0 → 0.1.1
  ✓ src-tauri/Cargo.toml  0.1.0 → 0.1.1
  ✓ src-tauri/Cargo.lock  0.1.0 → 0.1.1
  ✓ 校验通过：tauri.conf.json / package.json / Cargo.toml 三处一致

────────────────────────────────────────────────
下一步（由你自己执行，脚本不会碰 git）：

  git add -A && git commit -m "chore: 版本号 0.1.1"
  git push oneno-pet main
  git tag v0.1.1
  git push oneno-pet v0.1.1
```

看到最后那句「校验通过」才算成功。脚本**只改文件、不碰 git**。

**步骤 3 · 提交并推送代码**

```bash
git add -A && git commit -m "chore: 版本号 0.1.1"
git push oneno-pet main
```

**这一步不能省。** tag 指向的是某个 commit，如果版本号改动没提交，tag 就会打在旧 commit 上，
CI 构建出来的包和 `latest.json` 里还是旧版本号，客户端会一直说「已是最新」——
不报错、只是静默失效，最难排查。

**验证已推送：**

```bash
git log --oneline oneno-pet/main..HEAD   # 输出为空 = 已全部推送
```

**步骤 4 · 打 tag 并推送（触发 CI）**

```bash
git tag v0.1.1
git push oneno-pet v0.1.1
```

推完 tag，GitHub Actions 会**自动开始跑**，不需要你做任何额外配置或点击。

**验证 CI 已触发：** 打开 `https://github.com/Away6v/oneno-pet/actions`，能看到一条 `release` 记录，状态是黄点（in progress）。

**步骤 5 · 等 CI 跑完（约 7~8 分钟）**

流水线做的事，按顺序：

```
checkout → 装 Node → 装 Rust → 缓存 Rust 产物 → npm ci
  → 校验版本号一致（sync-version --check）
  → 校验 tag 与版本号一致
  → tauri-action：构建安装包 + 私钥签名 + 上传 Release 产物 + 生成 latest.json
```

**怎么知道跑完没有 —— 用脚本盯，别刷网页：**

```bash
npm run wait-release -- v0.1.1
```

它每 15 秒查一次，只在**状态有变化**时打印一行，跑完自动告诉你结果：

```
仓库：Away6v/oneno-pet   tag：v0.1.1
构建 #3  v0.1.1  2026-09-29T02:59:13Z
https://github.com/Away6v/oneno-pet/actions/runs/36515110711

[11:00:12] +0分59秒  … 进行中 · 已完成「安装前端依赖」
[11:02:03] +2分50秒  … 进行中 · 构建并发布
────────────────────────────────────────────────
✓ 构建成功（耗时 7分33秒）
✓ v0.1.1 已发布，且已是 latest
✓ 验签自检通过：客户端公钥与签名 keyID 一致（75E2CEF11686FF80）
```

**顺便记住这个容易吓人的现象：** 推完 tag 后，**「标签页」立刻**就有 `v0.1.1`，
但**「发行版页」在 CI 跑完前完全是空的**（草稿要等 `tauri-action` 建）。
两者是不同的东西 —— 标签页显示的是 git tag，发行版页显示的是 GitHub Release 对象。
**看到「标签页有、发行版页没有」先查 CI，不要怀疑配置。**

**为什么脚本不去 curl 确认草稿在不在：** 草稿在匿名 API 里**完全查不到** ——
`GET /releases` 不返回 draft，`GET /releases/tags/<tag>` 对草稿直接 404，
`/releases/latest` 和 `latest.json` 在 Publish 之前**仍显示旧版本号**（这是正确的，不是 bug）。
想确认草稿只能打开网页刷新。

**步骤 6 · 核对 Release 产物**

打开 `https://github.com/Away6v/oneno-pet/releases`，找到标题为 `oneno-pet v0.1.1`、
左边挂着灰色 **Draft** 标签的那条。

展开它的 **Assets**，**必须是这 3 个**：

```
latest.json
oneno-pet_0.1.1_x64-setup.exe
oneno-pet_0.1.1_x64-setup.exe.sig
```

（另外还会有 GitHub 自动附带的 `Source code (zip)` / `Source code (tar.gz)`，这两个跟你无关，正常。）

| 你看到的               | 含义                     | 该做什么                                  |
| ---------------------- | ------------------------ | ----------------------------------------- |
| 只有 Source code 两项  | CI 还在上传，或构建失败了 | 再等 1~2 分钟刷新；一直这样就去 Actions 看日志 |
| 有上面那 3 个          | 产物齐了                 | 可以进入步骤 7                            |
| CI 是红叉              | 构建失败                 | 去 Actions 看日志，修完删掉 tag 重打      |

**步骤 7 · 手动点 Publish release**

**为什么必须手动：** 流水线里配的是 `releaseDraft: true`，`tauri-action` 只创建**草稿**，不会自动发布。
而客户端读的 `releases/latest/` **只指向已发布且非预发布的 Release**，草稿不算。

**⚠️ 这个按钮不好找，别在草稿的展示页上找 —— 那页上根本没有发布按钮。**

草稿的展示页是**只读**的，右上角只有两个图标：**铅笔（编辑）** 和 **垃圾桶（删除）**。
发布按钮藏在编辑页里：

1. 在步骤 6 那个草稿卡片上，点右上角的**铅笔图标**（不是垃圾桶）
2. 进入编辑页后**滚到表单最底部**，点绿色的 **`Publish release`**
   （旁边那个 `Save draft` 是「继续存草稿」，别点错）
3. 点完，**`Draft` /「草稿」标签消失**，标题右边出现绿色 **`Latest` /「最新发行版」** 标签 —— 这才算发布成功

**捷径：** 直接访问编辑页，省掉第 1 步 ——

```
https://github.com/Away6v/oneno-pet/releases/edit/v0.1.1
```

> `Set as the latest release` 那个勾选框**不用管**：`0.1.1 > 0.1.0`，
> GitHub 会按语义化版本自动把它标成 Latest。

**步骤 8 · 验证**

**先验服务端：**

```bash
curl -sL https://github.com/Away6v/oneno-pet/releases/latest/download/latest.json
```

必须带 `-L`（这个地址是 302 跳转，不跟随会拿到空响应，容易误判成「清单不存在」）。

预期能看到：

```json
{
  "version": "0.1.1",
  "notes": "...",
  "pub_date": "2026-...",
  "platforms": {
    "windows-x86_64":       { "signature": "dW50cnVzdGVk...", "url": ".../v0.1.1/oneno-pet_0.1.1_x64-setup.exe" },
    "windows-x86_64-nsis":  { "signature": "dW50cnVzdGVk...", "url": ".../v0.1.1/oneno-pet_0.1.1_x64-setup.exe" }
  }
}
```

确认 `version` 是新版本号、`signature` 非空、`url` 指向新版本号的 exe。

**再用旧版客户端实测：**

打开**已安装的旧版本**（比如 0.1.0）→ 设置 → 软件 → 点「检查更新」。

| 阶段       | 预期界面                                                          |
| ---------- | ----------------------------------------------------------------- |
| 点击检查   | 按钮变「检查中…」并禁用                                            |
| 发现新版   | 「发现新版本 v0.1.1，可一键升级」+ 更新说明 + 「立即升级」/「稍后」 |
| 点立即升级 | 进度条推进，状态文案带百分比                                      |
| 下载完成   | 「正在安装，软件即将重启…」                                        |
| 安装完成   | 软件自动重启，「当前版本」变成 **v0.1.1**                          |

> 验证必须用**安装版**，不要用 `npm run tauri dev` —— dev 模式下 `getVersion()` 读的是开发时的配置，
> 升级行为也和安装版不一致。

### 6.3 验签密钥自检（不想装旧版时）

客户端内置的是 `tauri.conf.json` 里那把公钥，CI 用的是仓库 Secret 里那把私钥。
两者若不是一对，更新会一路下载成功、最后**卡在验签**上。比对 keyID 即可确认 —— minisign 的 keyID
是公钥 / 签名字节流的第 3~10 字节：

- 公钥：`~/.tauri/oneno-pet.key.pub` → base64 解码 → 取非 `untrusted comment` 那行 → 再 base64 解码 → `[2..10]`
- 签名：Release 里的 `*.exe.sig`（或 `latest.json` 的 `signature` 字段）→ 同上 → `[2..10]`

两边一致就是同一把密钥。当前项目的 keyID 是 **`75E2CEF11686FF80`**。

### 6.4 全流程检查清单

发版时对着勾一遍：

- [ ] 版本号比当前大，且没发布过
- [ ] `npm run set-version` 输出「校验通过」
- [ ] 版本号改动**已提交**（不是只改了文件）
- [ ] tag 名 == `v` + 版本号，且**在提交之后**才打的
- [ ] `npm run wait-release` 报「✓ 构建成功」（退出码 0，不是红叉也不是还在跑）
- [ ] 脚本报「✓ 验签自检通过」，keyID 一致
- [ ] Release 的 Assets 里有 3 个产物
- [ ] 点了 **Publish release**（铅笔图标 → 编辑页底部），`Draft` 变成 `Latest`
- [ ] `curl -sL` 出来的是新版本号
- [ ] 旧版安装包实测能一键升到新版

## 7. 排错速查表

| 现象                                                            | 原因                                                                                             | 处理                                                                                                     |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| **「标签页有 v0.1.1，但发行版页什么都没有」**                    | **不是故障**：标签页显示 git tag（一推就有），发行版页显示 Release 对象（要等 `tauri-action` 建草稿）。CI 跑完前发行版页是空的 | 跑 `npm run wait-release -- v0.1.1` 等它；**不要怀疑配置**                                                |
| **草稿页上找不到 `Publish release` 按钮**                        | 草稿展示页是**只读**的，上面根本没有发布按钮                                                     | 点卡片右上角的**铅笔图标**进编辑页，按钮在**表单最底部**；或直接开 `/releases/edit/v0.1.1`                |
| 客户端报 `Could not fetch a valid release JSON from the remote` | Release 里没有 `latest.json` 这个产物（常见于手动建了个空 Release，或 CI 还没传完）              | 看 Actions 是否跑完、Assets 是否有 3 个；等齐了再点检查更新                                              |
| 点检查更新报「网络连接失败」                                     | 国内访问 GitHub Release 附件域名超时                                                             | 用界面上的「手动下载」兜底；或挂代理后重试                                                               |
| 一直显示「已是最新 v0.1.0」，但 0.1.1 已发布                     | ① Release 还是草稿没 Publish ② tag 打在了没改版本号的 commit 上 ③ GitHub CDN 缓存                 | 逐条排查；③ 等 1 分钟重试                                                                                |
| 下载到中途失败，提示「网络中断，下载没完成」                     | 国内直连 GitHub 附件域名断流（reqwest 报 `error decoding response body`，字面意思有误导性）        | 脚本已自动重试一次；仍失败就点「手动下载」到发布页，或连代理后重试                                        |
| 下载完成但安装失败 / 没反应                                      | 验签失败：CI 用的私钥与客户端内置公钥不是同一对                                                  | 跑 `npm run wait-release` 看验签自检；或见 §6.3                                                          |
| CI 红叉，报「tag 与版本号不一致」                                | tag 名和 `tauri.conf.json` 的 version 对不上                                                     | 删掉 tag，改对版本号并提交，重新打 tag                                                                   |
| CI 红叉，报版本号不一致                                          | 三个文件版本号漂移                                                                               | 本地跑 `npm run sync-version`，提交后重打 tag                                                            |
| CI 红叉，报 `A public key has been found, but no private key`    | 仓库没配 `TAURI_SIGNING_PRIVATE_KEY` Secret                                                      | 去 Secrets 补上私钥**内容**                                                                              |
| 本地 `npm run tauri build` 报同样的「no private key」             | 开启 `createUpdaterArtifacts` 后本地打包也强制要签名                                             | 用 `npm run build:desktop`（自动注入私钥）；只做快速验证可加 `--no-sign`                                  |
| 本地打包卡在 `expect a prompt for password` 不动                 | CLI 在等私钥密码输入，后台跑表现为卡死                                                           | 用 `npm run build:desktop`（默认补空密码）；私钥真有密码就 export `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`    |
| 想重发同一个版本号                                               | tag 已存在，`git tag` 会报错                                                                     | 先删 tag（本地 + 远端），再重打                                                                          |
| `wait-release` 报「匿名配额已耗尽」                              | 匿名调 GitHub API 只有 60 次/小时，一轮等待约用 30 次；同小时内排查几次就会耗光                    | 等它重置（脚本会告诉你几点），或加 `--token <令牌>` / 设 `GITHUB_TOKEN`（5000/小时）。急的话先开 Actions 网页看 |
| 首次运行被 SmartScreen 拦                                          | 个人自用、无代码签名证书                                                                         | 属**独立问题**，不影响更新器工作；需付费证书才能消除                                                      |

## 8. 发错了怎么办

**草稿发错了 / 产物不对：**
删掉草稿 Release，删掉 tag（本地 + 远端），修好代码后重新走一遍流程：

```bash
git tag -d v0.1.1                      # 删本地 tag
git push oneno-pet :refs/tags/v0.1.1   # 删远端 tag
```

**已经发布了，但发现 bug：**
**不要删 Release**，直接发一个更高的版本（如 0.1.2）覆盖过去。
客户端读的是 `releases/latest/`，新版本发布后 `latest` 自动指向它，老用户下次检查更新就会升上来。

**只是想撤回客户端的更新提示：**
把 Release 改回草稿（Release 页面点 `Edit` → 勾选 `Set as a draft`），
`releases/latest/` 就会重新指向再上一个已发布的版本。

## 9. 铁律（别做的事）

**1. 不要跳过「提交」直接打 tag。**
tag 指向 commit，不提交就 tag，CI 构建出来的还是旧版本号，客户端永远说「没有新版」。这是最隐蔽的失败方式。

**2. 不要在 GitHub 网页上手动建 Release。**
手动建 + Publish 会造出一个**只有 Source code、零产物**的 Release，它立刻成为「latest」，
`latest.json` 就变成 404，客户端立刻报错。正确做法是**只推 tag**，让 CI 建草稿，等 CI 绿了再 Publish。

**3. 不要忘了点 Publish release，也别在草稿展示页上找它。**
草稿对 `releases/latest/` 不可见，不点发布等于没发。
而草稿的**展示页是只读的，上面根本没有发布按钮** —— 要点卡片右上角的**铅笔图标**进编辑页，
按钮在表单最底部。找不到就直开 `https://github.com/Away6v/oneno-pet/releases/edit/v0.1.1`。

**4. 不要用 `git push origin`。**
本仓库 remote 名是 `oneno-pet`。

**5. 不要改已发布版本的 `endpoints`。**
`plugins.updater.endpoints` 是**编译进二进制**的，发出去的客户端只认那一个地址，
改了等于让所有老用户永久失联。第一次发布前就要定死。

**6. 不要用 `npm run tauri build` 打包。**
用 `npm run build:desktop`（会自动注入签名私钥）。

**7. 不要删已发布的 Release。**
`releases/latest/` 会因此失去指向，客户端报错。
